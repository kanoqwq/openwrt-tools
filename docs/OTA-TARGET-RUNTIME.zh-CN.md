# 网页生成差分后，更新器停留在旧版

2026-11-13，E5 现场版本已是 `r20261113.141316-geae49c9d-s14d8b935`，
但实际 builder、RPC、页面、ACL 均为旧程序，不含 `discard_generated`。
只读检查设备保留的差分包：manifest 仅有 7 项系统变更，RAM runtime 中
上述四份文件的摘要与设备旧文件一致。不是浏览器缓存，也不是新版完整根缺文件。

原因在公共 `generator/ota_package.py:compare()`：为支持首次从无更新器系统
迁移，生成器把自己携带的更新器无条件覆盖到新包 entries。设备用旧生成器
处理新版 ZIP 时，新版内置更新器被旧副本替换；release_index 同样记下了
替换后的旧副本，因此版本号前进但更新器不升级。

修正边界：

- 执行本次安装的 RAM 程序仍来自生成器，继续使用它支持的协议和隔离环境。
- 新版根已内置 `usr/lib/unisoc-ota/engine.py` 时，安装文件及目标基准完全取自
  该新版根；不得用生成器的页面、权限、核心或生成器文件覆盖它。
- 目标根没有内置更新器时，保留原有首次迁移安装，不取消旧系统迁移能力。
- 不改用户配置、账户、NV、数据保留与本地小修改的处理，不增加版本/哈希白名单。

回归直接生成真实 fixture `.ota`，比较七份目标文件的操作、blob 内容与
release_index，并验证 RAM 程序和安装程序可以不同；未变化的内置更新器
不应因工具版本不同被替换。原有首次迁移、页面/权限安装、事务、撤销和
本地系统修改保留测试一并执行，`tests/test_ota.py` 53 项通过。

已经安装的旧生成器不会因为收到新 ZIP 自动获得本修复。现有设备需先更新
更新器组件，或使用修正版桌面工具生成差分包，再由原有检查/确认流程安装。
不能让用户在旧网页中重复生成同一对 ZIP 期待结果改变。
